# 设计决策记录

记录关键架构选择背后的理由，便于后续维护者理解"为什么是这样"，以及避免重蹈讨论。

---

## D-001：主交互模式 = Discover（发现），不是 Search（查询）

**决策**：默认入口是浏览算法挖掘的押韵 cluster，而非传统"输入词组 → 查韵脚"。

**理由**：
1. 大部分随手输入的短语（例："原神芭芭拉"）在中文里没有好的多音节押韵匹配 → Search 模式高失败率
2. 押韵是 rapper 写词的**结果**而不是**起点** —— 真正卡住创作的是"想到 clever 组合"，不是"查韵脚"
3. Pinterest 模式 > Google 模式：主动推送 + 浏览发现 比 被动应答 更适合创作工具

**Search 和 Analyze 仍然保留**，但作为辅助模式。

---

## D-002：押韵匹配 100% 走确定性算法，不让 LLM 生成韵脚

**决策**：拼音 → 韵母 → 韵组查询全部由代码 + 静态表完成。LLM 仅在"解读为什么这组押韵巧妙"等只读场景按需触发。

**理由**：实测 Claude Opus 4.6 生成押韵候选的准确率不到 80%。22 条候选中至少 5 条韵母完全错（"蒋琬发力" 被标为 iang-ui-a-i 实际是 iang-an-a-i；"项羽得意" 被标为 iang-ui-e-i 实际是 iang-ü-e-i）。剩下押对的里有大量被韵脚硬绑架出来的废话（"酱归发币"、"项随发起"、"墙推发力"等）。

**根本原因**：LLM 在 BPE token 上工作，看不见音素。押韵是硬约束，LLM 是概率生成 —— 原理上不匹配。即使 prompt 极其精确，LLM 仍会在多个位置随机出错。

**替代方案**：用大语料 + 智能切片（整体匹配、2+2 拼接、模板填充）从真实文本中挖出"姜维的戏"级别的创意组合 —— 它们本来就在《三体》、三国典籍、说唱歌词里，不需要 LLM 转述。

## D-003：技术栈 = TypeScript + SvelteKit + Tailwind + GitHub Pages

**决策**：纯前端 TypeScript，编译为静态站部署到 GitHub Pages。

**演进过程**：
1. 最初选 Python + Gradio → 被指出 UX 上限太低
2. 改 FastAPI + 前端分离 → 被指出部署复杂、有冷启动
3. 改 Rust → WASM → 被指出工程复杂度过高、生态收窄
4. 最终落在 TypeScript + SvelteKit → 性能足够、贡献者门槛低、零服务器

**性能验证**：500k 词条规模下的查询是哈希查表 + 集合操作，V8 在微秒级完成，离 JS 性能瓶颈差几个数量级。词库用 TypedArray 紧凑存储，内存占用与 Rust 相当（~25MB vs ~20MB）。

**Python 仍保留**，但仅用于离线数据准备脚本（爬虫、清洗、质量打分、cluster 挖掘）。运行时与 Python 无关。

## D-004：分级宽松搜索（用户不手动标位置）

**决策**：Search 模式下，系统自动从 Level 0（全严格）到 Level N（多位放宽）穷举展示，按层级折叠。用户不需要手动指定哪个位置可以宽松。

**理由**：手动标注是认知负担。穷举所有"放几位 + 哪几位"是有界的（10 位时最多 2^10 = 1024 种组合），完全可计算。

## D-005：质量打分体系（避免"垃圾词"）

每条入库词条计算复合质量分（0-1）：

```
quality_score =
    0.25 × domain_frequency_score    # 在目标语料（rap/歌词）中的频率
  + 0.20 × cultural_relevance_score  # 文化梗、专有名词
  + 0.15 × lyrical_attestation       # 是否真的出现在歌词中
  + 0.15 × pos_validity              # 词性结构合理性
  + 0.10 × distinctiveness           # TF-IDF，避免烂大街
  + 0.10 × surprise_score            # 跨域组合度
  − 0.20 × blacklist_penalty         # 粗口/敏感
  − 0.10 × common_filler_penalty     # "的""了"开头扣分
```

`quality_score < 0.3` 不入库。索引时分 S/A/B/C/D 五档，UI 默认只展示 A 档以上。

## D-006：Cluster 巧妙度评分（决定 Discover 推什么）

```
cleverness =
    平均成员质量分                  # 个个都是好词
  × 领域跨度                       # 三国×科幻×电竞 > 全是同义词
  × 新鲜度（1 − 主流歌词出现率）    # 没被用滥
  × log(押韵长度)                  # 4 押 > 2 押
  × min(成员数, 8) / 8             # 至少要有几个成员才有用
  × 意外性                         # 同 cluster 内成员"看起来无关"
  − 低俗/敏感词扣分
```

**关键**："巧妙"≠"押得严"。一个 8 押但全是同义词凑的，不如一个 4 押但跨三国/科幻/电竞的。

## D-007：用户系统 = 无（仅 localStorage）

**决策**：Phase 1 不做账户/登录。收藏、偏好等都存浏览器 localStorage。

**理由**：避免后端 + 数据库 + 鉴权 的全套复杂度。Phase 1 之后再视用户量决定是否引入。

---

## D-008：LLM 提供商策略

**决策**：用户自填 API key，前端直接 fetch 调用，不经过任何中转服务器。
- 默认支持 Anthropic Claude / OpenAI / DeepSeek（用 LiteLLM 风格的统一适配）
- 支持本地 Ollama 端点
- key 仅存浏览器 localStorage，不上传

---

## D-009：英文/中英混押

**决策**：维护一份 rap 圈常用英文词的"汉语化韵母"静态表（如 `flow → ou`，`beat → i`，`swag → a`）。从英文 rap 歌词语料挖掘扩充。
不让 LLM 即兴音译（同 D-002 理由，会幻觉）。

---

## D-010：分享卡片图（社交传播）

Discover 卡片支持一键生成图片导出，便于分享到社交平台。Phase 1 P2 任务。

## 决策风格

未来变更架构时请遵循同样标准：每个默认选择都要能用具体需求和数据论证，不接受"约定俗成"或"行业最佳实践"作为理由。
